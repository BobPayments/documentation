Uma integração completa cria a transação no backend, apresenta o PIX na interface e confirma o pagamento por webhook.

```text
Comprador ── solicita pagamento ──> Seu backend ── cria transação ──> API Bob
    │                                      ▲                            │
    └── vê e paga o PIX                    └── confirma o pedido <── webhook
```

## O que cada parte faz

| Parte | Responsabilidade |
|---|---|
| Seu backend | Guarda a chave, cria a transação e recebe webhooks |
| Sua interface | Mostra o `pixCode`, o QR Code e o estado atual |
| API Bob | Cria a cobrança e informa seu estado |
| Webhook | Confirma mudanças como pagamento ou expiração |

## Implemente em cinco etapas

<Steps>
  <Step title="Autentique no backend">
    Envie `Authorization: Bearer sk_test_sua_chave` em cada chamada. [Veja como criar e proteger a chave](/pages/authentication).
  </Step>
  <Step title="Crie uma transação">
    Envie cliente, valor e produto para `POST /api/v1/transactions/`. Envie também `Idempotency-Key` se usar a API REST. [Consulte a operação](/pages/pix/create).
  </Step>
  <Step title="Apresente o PIX">
    Mostre o `pixCode` como código copia-e-cola ou transforme-o em QR Code. Um HTTP `201` confirma apenas a criação da cobrança.
  </Step>
  <Step title="Confirme pelo webhook">
    Valide a assinatura e libere o pedido somente depois de receber `transaction.paid`. [Implemente o endpoint](/pages/webhooks).
  </Step>
  <Step title="Trate os outros estados">
    Atualize a interface quando a transação expirar, for cancelada ou for reembolsada.
  </Step>
</Steps>

## Use os estados corretos

| Estado | O que sua aplicação deve fazer |
|---|---|
| `waiting_payment` | Mostrar o PIX e aguardar |
| `processing` | Informar que a confirmação está em andamento |
| `paid` | Liberar o pedido após validar o webhook |
| `expired` | Encerrar a tentativa e oferecer uma nova cobrança |
| `cancelled` | Encerrar a tentativa |
| `refunded` | Atualizar o pedido como reembolsado |

Não use o retorno da criação como confirmação financeira. O pagamento acontece de forma assíncrona.

## Checklist da integração

- [ ] A chave de API existe somente no backend.
- [ ] Todos os valores são enviados em centavos.
- [ ] A criação usa uma `Idempotency-Key` por pedido.
- [ ] A interface mostra o `pixCode` retornado pela API.
- [ ] O endpoint de webhook valida a assinatura com o corpo bruto.
- [ ] O processamento de `transaction.paid` é idempotente.
- [ ] Os estados `expired`, `cancelled` e `refunded` são tratados.
- [ ] O fluxo completo foi testado com `sk_test_`.
